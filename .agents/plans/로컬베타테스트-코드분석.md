# 메디허브 로컬 베타 테스트 코드 분석

작성일: 2026-03-22

## 한줄 결론

- 현재 코드베이스는 `리드 생성 -> 업체 수신 -> 상태 변경 -> 과금/환불 -> 기본 운영 통계`까지는 꽤 진행되어 있습니다.
- 다만 이번 베타 플랜 기준으로 보면 `보안 필수 항목`, `관리자 관제 화면`, `업체별 응답률/평균 응답시간 운영 지표`, `문자 발송 기반 운영`, `관리자 크레딧 수동 조정`은 아직 부족합니다.
- 따라서 지금 상태는 `제한적인 내부/소규모 클로즈드 베타`는 가능하지만, 문서에 적힌 운영형 2주 베타를 그대로 돌리기에는 운영 도구와 보안 항목이 덜 갖춰진 상태입니다.

## 총평

### 구현됨

- 역할 분리와 기본 권한 모델
  - `doctor / vendor / admin` 역할 분리는 구현되어 있고, 공통 가드도 있습니다.
  - 근거: `app/src/server/auth/guards.ts:39-45`, `app/src/server/auth/guards.ts:109-137`
- 업체 간 리드 접근 차단, 의료인은 본인 문의만 조회
  - RLS에서 doctor는 자기 리드만, vendor는 자기 업체 리드만, admin은 전체 조회가 가능합니다.
  - 근거: `app/supabase/migrations/20251218190000_p0_schema.sql:799-850`
- 리드 생성 핵심 플로우
  - 리드 생성 시 doctor 매핑, vendor 매핑, 내용 저장, 상태 `submitted` 저장, 상태 이력 기록이 됩니다.
  - `id`, `created_at`은 DB 기본값으로 자동 생성됩니다.
  - 근거: `app/src/app/api/leads/route.ts:155-215`, `app/supabase/migrations/20251218190000_p0_schema.sql`의 `leads` 테이블 기본 스키마
- 리드 상태 변경 및 히스토리

  - 근거: `app/src/app/api/cron/lead-no-response/route.ts:30-125`, `app/src/server/lead/repository.ts:349-436`

### 부분구현

- 관리자 승인 후 활성화 구조
  - 검수 승인 전 doctor/vendor 핵심 액션은 막혀 있습니다.
  - doctor 문의 생성은 승인 doctor만 가능하고, vendor 주요 API도 승인 vendor 가드가 붙습니다.
  - 근거: `app/src/server/auth/guards.ts:47-81`, `app/src/app/api/leads/route.ts:55-57`, `app/src/app/api/credits/charge/route.ts:12-27`
  - 다만 계정 자체는 일반 회원가입 후 바로 생성되며, 전역적으로 "관리자 승인 후 계정 활성화" 구조는 아닙니다.
  - 근거: `app/src/app/(auth)/signup/page.tsx:78-123`, `app/src/app/api/profile/route.ts:13-98`
- 전체 리드 조회
  - admin은 RLS상 전체 리드 조회가 가능하고, 공용 `GET /api/leads`와 리드 CSV export도 사용할 수 있습니다.
  - 근거: `app/src/app/api/leads/route.ts:16-52`, `app/supabase/migrations/20251218190000_p0_schema.sql:819-823`, `app/src/app/api/exports/leads/route.ts:6-25`
  - 하지만 `/admin/leads` 같은 전용 운영 화면은 없습니다. 운영 UX 기준으로는 반쪽입니다.
- 리드 통계
  - 관리자 대시보드에 전체 리드 수, 기간 리드 수, 상태 분포, 전환율은 있습니다.
  - 근거: `app/src/server/analytics/service.ts:182-220`, `app/src/lib/schema/analytics.ts:83-98`, `app/src/app/(main)/admin/dashboard/leads/page.tsx:23-101`
  - 다만 베타 플랜에서 필요한 `업체별 리드 수`, `업체별 응답률`, `업체별 평균 응답시간`, `72시간 SLA 준수율`은 관리자 분석 API에 없습니다.
- 응답률/평균 응답시간 계산 로직
  - 응답률 계산은 비딩 추천용으로 존재합니다.
  - 근거: `app/src/server/bidding/scoring-service.ts:219-250`
  - 평균 응답시간 계산도 배지 부여용으로 존재합니다.
  - 근거: `app/src/server/badge/repository.ts:120-163`, `app/src/server/badge/service.ts:39-48`
  - 다만 이 값들이 관리자 운영 화면이나 베타 보상 정책에 직접 연결되어 있지는 않습니다.
- 알림 발송과 발송 로그
  - 이메일/카카오 발송과 `notification_deliveries` 기록은 구현되어 있습니다.
  - 근거: `app/src/server/notification/service.ts:399-428`, `app/src/server/notification/service.ts:451-618`, `app/src/server/notification/repository.ts:88-127`
  - 다만 베타 문서가 말하는 "문자 발송 API"는 현재 SMS가 아니라 `이메일 + 카카오 알림톡` 중심입니다.
  - `sms` 채널 enum은 있지만 실제 SMS 발송 로직은 보이지 않습니다.
  - 근거: `app/supabase/migrations/20260117120000_notification_settings.sql:4-12`, `app/src/server/notification/solapi.ts:21-27`
  - 또한 관리자용 발송 로그 조회 API/UI는 없습니다.
- 리드 상태 변경 로그 조회
  - `lead_status_history` 저장 자체는 됩니다.
  - 근거: `app/src/app/api/leads/route.ts:205-215`, `app/src/app/api/leads/[id]/status/route.ts:54-63`
  - 리드 상세 API에도 히스토리가 포함됩니다.
  - 근거: `app/src/server/lead/repository.ts:38-74`
  - 하지만 관리자 전용 상태 이력 조회 화면이나 목록 API는 없습니다.
- 서버 로그 저장
  - API 공통 에러는 Sentry로 보내고, 여러 서비스에서 `console.error`와 delivery/audit 로그를 남깁니다.
  - 근거: `app/src/server/api/with-api.ts:6-25`, `app/sentry.server.config.ts:1-7`, `app/sentry.client.config.ts:1-14`
  - 다만 "운영 로그 저장 시스템"으로 보기엔 구조화된 앱 로그 저장소는 부족합니다.
- 비밀번호 암호화 저장
  - 앱이 직접 비밀번호를 저장하지 않고 Supabase Auth의 `signUp/signInWithPassword`를 사용합니다.
  - 근거: `app/src/app/(auth)/signup/page.tsx:81-87`, `app/src/app/(auth)/login/page.tsx:62-66`
  - 따라서 비밀번호 자체를 코드베이스가 따로 평문 저장하는 흔적은 없지만, "우리 코드에서 암호화 구현"이 있는 형태는 아닙니다.
- DB 외부 접근 차단
  - 코드 차원에서는 RLS, server-only admin client, client-side direct DB 금지 패턴은 잘 잡혀 있습니다.
  - 근거: `app/supabase/migrations/20251218190000_p0_schema.sql:497-920`, `app/src/server/supabase/admin.ts:6-20`, `app/src/server/supabase/server.ts:7-30`
  - 다만 Supabase 네트워크 레벨 접근 차단, IP allowlist, 대시보드 보안 설정은 저장소만 보고는 보장할 수 없습니다.

### 미구현 또는 부족

- 초대 링크 기반 회원가입
  - 회원가입 화면은 일반 이메일/소셜 가입만 있고, invite token/초대 링크 처리 흐름이 없습니다.
  - 근거: `app/src/app/(auth)/signup/page.tsx:46-123`
  - 저장소 전역 검색 기준으로 invite/onboarding token 기반 가입 구현은 확인되지 않았습니다.
- 관리자 2단계 인증
  - 관리자 MFA/TOTP/factor 검증 코드는 확인되지 않았습니다.
  - 근거: `app/src/server/auth/guards.ts:100-137`에는 role 체크만 있고, 저장소 검색 기준 `mfa|totp|factor|2fa` 구현 흔적이 없습니다.
- HTTPS 적용 완료 보장
  - `NEXT_PUBLIC_SITE_URL` 기본값은 HTTPS이고 metadata도 HTTPS 기반입니다.
  - 근거: `app/.env.example:32-40`, `app/src/app/layout.tsx:17-33`
  - 하지만 강제 리다이렉트나 배포 인프라 수준 HTTPS 보장 로직은 저장소에서 확인되지 않습니다.
- 리드 열람 시간 기록
  - 메시지 `read_at`은 있지만, 리드 자체를 업체가 언제 열었는지 기록하는 `viewed_at/opened_at`은 보이지 않습니다.
  - 근거: `app/src/server/lead/message-repository.ts:175-221`, 저장소 검색 기준 `viewed_at|opened_at` 없음
- 관리자 크레딧 지급/차감 수동 조정
  - 현재 크레딧 API는 vendor 본인 충전/거래내역/자동충전 설정만 있습니다.
  - 근거: `app/src/app/api/credits/route.ts:11-16`, `app/src/app/api/credits/charge/route.ts:12-27`, `app/src/app/api/credits/transactions/route.ts:12-20`
  - 서버 service/repository에도 admin 수동 증감용 API/서비스가 없습니다.
  - 근거: `app/src/server/credit/service.ts:39-234`, `app/src/server/credit/repository.ts:8-248`
- 관리자용 문자 발송 로그 조회
  - `notification_deliveries` 저장은 있지만, 이를 조회하는 admin API/UI가 없습니다.
  - 근거: `app/src/server/notification/repository.ts:88-127`, `app/src/api-client/admin.ts:182-295`
- 업체별 베타 보상 조건 자동 판정
  - `응답률 80%`, `평균 응답시간 24시간`, `인터뷰 참여`, `정책 위반 없음`을 묶어 자동으로 추가 크레딧 지급하는 로직은 없습니다.
- 허위 문의 자동 필터
  - refund reason enum에 `fraud_auto_filter`는 있지만, 실제 자동 탐지/자동 차단 로직은 확인되지 않았습니다.
  - 근거: `app/src/lib/schema/lead.ts:81-88`, `app/supabase/migrations/20260228141000_lead_charges.sql:14-17`

## 지금 상태에서 베타를 열면 생길 운영 리스크

- 업체 응답률/응답시간을 기준으로 `추가 크레딧 150,000원` 지급 여부를 자동 판정할 수 없습니다.
- "문자 미수신" 같은 장애를 운영자가 관리자 화면에서 바로 추적할 수 없습니다. 로그는 남지만 조회 UI가 없습니다.
- 관리자가 리드 흐름을 한 화면에서 쭉 보는 운영 콘솔이 없어, CSV export나 공용 API에 의존해야 합니다.
- 72시간 정책은 존재하지만 cron이 하루 1회라, 베타 운영 문서처럼 촘촘한 SLA 관제에는 부족합니다.
- 보안 체크리스트 중 `관리자 2FA`, `HTTPS 보장`, `DB 외부 접근 차단`은 코드 저장소만으로는 완료 상태라고 보기 어렵습니다.
